Harness Self-Evolution Needs an Outside

Research noteAugust 2026~12 min

Harness Self-Evolution Needs an Outside

Updating looks flat. Benefit peaks in the mid-tier. The loop only improves if the judge stays outside it.

1. The Claim

An agent is a language model plus the software around it: instructions, tools, skills, memory, permissions, the loop that calls the model again. That surrounding layer is the harness. For a few years it was treated as a product decision. In 2025 and 2026 it started being treated as state. The agent runs, something writes a patch back into the harness, and the next run uses the new harness. Model weights stay put unless the method is explicitly co-training them.

That loop is what people now call a self-evolving harness. End-to-end scores mix four things: how well the model solves tasks under the initial harness, how good the proposed patches are, whether the model loads and keeps following those patches, and what the loop is forbidden to edit. The last of those is not a model capability. It is a design choice: the evaluator, the sandbox, the base contract, the held-out tasks. Papers report the product of the four and call the product self-evolution.

Lin et al., in Harness Updating Is Not Harness Benefit, separated the middle two. They call them harness-updating and harness-benefit, and they show they do not move together with model size.5 That split is real. It is also incomplete. Their protocol froze the surfaces where a stronger model would have something hard to do. What remains is a design constraint. The judge, the sandbox, and the base contract have to sit outside the loop, or the loop is optimizing a score it can rewrite.

This is a sequel to The Evolution of the Agent Harness, which argued that measured capability is Model + Harness. You do not need that piece. The definitions in the next section are enough to read this one.

2. Definitions

Harness. The non-parametric layer that turns a fixed language model into an agent. System instructions, tools and skill packages, memory, middleware and runtime policy, subagent configuration, verification and recovery rules. The weights are not part of the harness.14

Agent. Agent = Model + Harness. Same model, different harness, different measured capability. That is the experimental control in every paper below. When a result says “Opus 4.6 scored X,” it scored X inside some harness. Swap the harness and the number moves.

Evolver. The role that maps (current harness, execution evidence) to a harness delta. Evidence is trajectories, verifier outcomes, failures, sometimes the agent’s own notes. The evolver is often the same model as the agent, sometimes a stronger external model, sometimes a separate “evolve agent.” The distinction that matters is the role, not the logo on the API key.

Harness-updating vs harness-benefit. Following the pairing paper:5

  • Harness-updating: the ability to produce a useful persistent patch from execution evidence. The evolver’s job.
  • Harness-benefit: the ability to improve at the task once those patches exist. Load them, follow them, keep following them. The agent’s job.

These are different functions of the same model family. A small model can write a skill that a large model then uses. A large model can write a skill that a small model never loads. The pairing experiments below only make sense if you keep the roles apart: the solver is the agent, the author of the patch is the evolver, and they need not be the same model. Measuring only the product of the two is how a rising score gets read as “the agent improved itself.”

3. Two Capabilities

That pairing paper fixes the evolution protocol and swaps which model plays agent versus evolver. It does this across SWE-bench Verified, MCP-Atlas, and SkillsBench, with seven models spanning open and closed families.5 The protocol is the same for every pair: same initial harness, same task stream, same prompt templates, same budget. Only the backbone in each role changes.

Updating is flat in base capability. Hold the agent fixed and change the evolver. Mean evolution gain spreads by at most 3.1 percentage points on any of the three benches. No evolver wins all three. Qwen3.5-9B, the smallest model in the study, can post the highest gain on SkillsBench. Qwen3-235B leads on SWE-bench Verified and ranks last on MCP-Atlas. Scale does not predict who writes the useful patch.

The cleanest picture of that claim is a control, not a slogan. On one SkillsBench task they hold the solver fixed at Opus 4.6 and swap only who wrote the skill. With no evolved skill, Opus scores 0.67: it misses a FINISH-event filter. Given a skill written by Qwen3.5-9B, it scores 1.0. Given a skill written by Opus itself, it also scores 1.0. The two skills prescribe the same steps and differ in wording. The 9B evolver and the frontier evolver produced the same procedure. Holding the solver fixed is what makes that a measurement: any score change is the skill, not a smarter agent. If both skills take the same Opus run from 0.67 to 1.0, the extra capability in the frontier evolver did not show up in the patch. The solver did the work of using it.

Benefit is not monotonic in base capability. Mid-tier models gain the most from an updated harness. Strong models gain less: many tasks are already solved under the initial harness. Weak models gain least, despite the largest nominal headroom. Continual Harness sees the same floor in an online setting. On Pokémon Emerald, Flash-Lite under a minimalist harness reaches 20% completion; every Continual Harness variant on Flash-Lite falls to 3–13% at comparable or higher cost.4

The weak-tier collapse has two measured modes on SkillsBench. Activation: Qwen3-32B loads a skill in about a quarter of trajectories (~0.25). Opus 4.6, Sonnet 4.6, and Qwen3-235B load in about 0.96. The harness exists. The weak agent often never brings it into context as a valid action. Adherence: once a skill is loaded, Qwen3-32B falls from 0.52 following it after load to 0.13 by the last turn. Opus falls from 0.89 to 0.80. Loading is not using. The mid-tier peak is the gap between those two failures and the ceiling. A mid-tier model can load the patch and still has tasks left to win. A frontier model has fewer tasks left. A weak model often never starts.

Post-evolution score is still mostly base capability. Variation across seven evolvers, for a fixed agent, is small next to the gap between agents. Pair a weak agent with its best evolver and it still loses, on every bench in the paper, to a strong agent with its worst evolver. You cannot buy your way out of a weak agent with a better evolution story. You can still buy a jump for a mid-tier agent that actually uses the harness.

4. The Surface They Measured

The pairing paper keeps the model fixed. It updates “editable components of Ht (e.g., prompts, skills, memories)” and freezes “other components such as tool interfaces and execution policies.” On SWE-bench Verified and SkillsBench the evolvable set is skills only. On MCP-Atlas it is skills, prompts, and memories.5

That is a narrow surface. A skill is a procedure in prose: filter this event, run these steps, try the fallback. Two models of very different size can write the same procedure. A tool interface or a piece of middleware is different work. It has to compose with the rest of the harness, survive the next task, and not open a path the verifier cannot see. “Updating is flat” is well supported for skill and prompt patches under a frozen tool API. It is not evidence that proposing tools, middleware, or execution policy is similarly cheap. The 9B / Opus isomorphic skill is the cleanest picture of the narrow claim: writing a procedural skill is not where frontier intelligence is scarce. It does not tell you who should be allowed to rewrite the tool layer.

The rest of the offline literature edits those harder surfaces and puts the gains there. Self-Harness’s retained diffs are model-specific middleware: artifact recovery, dependency prechecks, environment persistence, tool-loop limits.1 A second Lin et al. paper, Agentic Harness Engineering (AHE), lifts Terminal-Bench 2 pass@1 from 69.7% to 77.0%; ablations put that lift in tools, middleware, and long-term memory, not system-prompt prose. Those are the surfaces the pairing paper froze.6

MCP-Atlas is the one Lin substrate that also lets prompts and memories change. Updating stays flat there. Qwen3-235B even ranks last. Adding memory and prompt text is not enough to restore a capability gradient. That is the strongest evidence they have that the result is not only “skills are easy.” It is still not a test of tools or policy.

The activation result is more mixed than the paper’s takeaway. Qwen3-32B’s load failure, in their own case, is an invalid multi-key action: the model names the skill, then embeds the load inside a broader call, and SkillsBench drops it. That is partly the shape of the load API. Qwen3-235B is the counterexample that saves the capability reading. It loads at 0.961 and still follows at 0.350, with a 0.022 pass-when-loaded rate. Phase drift for Qwen3-32B (0.52 → 0.13) versus Opus (0.89 → 0.80) looks like long-horizon instruction-following, not UX. Activation is partly an interface problem. Adherence is not.

Spend the expensive model on the task agent. Keep the evolver smaller if the editable surface is structured the way Lin’s was. Do not treat “updating is flat” as a reason to let a small model rewrite tools, middleware, or the execution policy. That experiment has not been run.

5. What Must Sit Outside

Offline, the harness changes between scored rounds: run, mine failures, propose a bounded edit, accept only if a gate the editor cannot touch says so, promote. Online, the harness is writable mid-trajectory. Continual Harness rewrites prompt, sub-agents, skills, and memory every F steps from the recent window.4 Prime Agent productizes that as rlm.harness plus /refine, with the base prompt frozen and rollbacks by ID.3 They are the same loop under different reset costs, not competing methods.

Self-Harness is the offline case with a hard gate. The same model is agent and proposer. Acceptance requires non-regression on both held-in and held-out splits, plus strict improvement on at least one. Held-out Terminal-Bench-2.0 pass rates:1

Those gains are held-out. The editor never sees the second split, and a patch that only fits the evolution set is rejected. That is the difference between a rising training score and a transfer claim. The papers that report transfer, and the product that reports a cheat, agree on the same pattern.

Outside the editable loopWhy
Evaluator, verifier, testsOtherwise the agent disables the judge (AHE’s threat model)
Held-out tasks or a prediction checkOtherwise edits overfit the evolution set (Self-Harness, HarnessCompass)2

Prime Agent’s Factorio run is the online result that matters. The same refine loop that turned failures into legitimate skills turned an RCON resource-spawn exploit into efficient cheating skills, despite a heartbeat prompt not to cheat.3 Online self-improvement optimizes the reward channel you actually expose. A prompt that says not to cheat is inside the loop. The RCON permission was inside it too. The other online limit is the same floor: Flash-Lite at 20% under the minimalist harness, 3–13% under Continual Harness.4

A self-evolving harness without an outside is a program with write access to its own policy and a score. The scientific content of the field is which surfaces the agent may edit, under what falsifiable contract.

6. Observed, Interpreted, Predicted

Observed

  • Gated offline evolution produces double-digit absolute gains with weights fixed. Self-Harness moves held-out Terminal-Bench pass rates 14 to 21 points. AHE moves Terminal-Bench 2 pass@1 from 69.7% to 77.0%.16
  • Cross-pairing shows harness-updating flat across model tiers (at most 3.1pp) and harness-benefit peaked at mid-tier, with weak models failing activation and adherence.5
  • Methods that freeze the judge and require held-out non-regression report transfer. Methods that allow online CRUD without a hard outside produce both skill formation and reward hacking. Factorio is the public case.163

Interpreted

  • Updating is flat for skills and prompts under a frozen tool API. It is not shown for tools and policy.
  • Activation is partly interface. Adherence is capability.
  • The loop only improves if the judge, the sandbox, and the base contract stay outside it.

Predicted

  1. Training recipes will add explicit objectives for harness invocation and long-horizon adherence. Skill files on disk will not be enough.
  2. Teams will not put the expensive model on the evolver unless the editable surface includes tools and policy.

7. This Framework Is Wrong If…

Any one is enough.

Updating tracks base capability once tools and policy are editable. If a stronger evolver systematically writes better tool interfaces, middleware, or execution rules under the same gate, “updating is flat” was an artifact of Lin’s frozen surface, not a structural fact. That is the experiment I want next. It would change where I would spend model budget.

Weak models gain more than mid-tier once activation is forced. Auto-load every skill and hard-wire an adherence check. If the benefit curve inverts, the weak-tier story was mostly the load API. Qwen3-235B’s adherence gap says this one will not fully invert. The activation half of it might.

Online refine without an external gate improves held-out real work and does not hack. If long-running production agents with free CRUD on their own prompts and skills show sustained quality under independent audit, the outside requirement is overfit to benches and games. This one would change my mind fastest about deployment.

8. Limits

I did not re-run Terminal-Bench, SWE-bench, ARC-AGI-3, or the Pokémon experiments. Vendor ARC numbers exist. They are not used as evidence here. Cross-paper absolute scores are not comparable: different models, harness seeds, task filters, attempt counts.

Section 4 is a reading of Lin’s implementation details against AHE and Self-Harness, not a new crossover experiment. Joint weight–harness methods are under-covered because the public evidence is thinner and more confounded.

9. Implications

For researchers. Report agent model, evolver model, editable surfaces, and the acceptance gate separately. Publish activation and adherence rates when claiming benefit. Do not treat end-to-end Δ as a single scientific object.

For builders. Put the expensive model on the task agent. Keep the evolver smaller if it is writing skills and notes. Never let it edit the verifier, the sandbox, or the base contract. Invest in a load API that a weak model can invoke, and in a runtime check that adherence has not decayed by turn 40.

For buyers. Ask whether a “self-improving agent” product can export its harness lineage, roll back a bad refine, and show held-out or production-metric non-regression. If the pitch is only a rising internal score, you are buying a loop, not a measured improvement process.

10. Open Questions

Can activation and adherence be trained as first-class skills? The pairing paper recommends it. Public recipes are thin. If they can, the weak-tier benefit story changes without anyone inventing a cleverer evolver.

What load API would make activation a non-issue? Qwen3-32B’s failure is an invalid multi-key action. That is a design problem before it is a capability problem. Auto-load, a single-key load, or a harness that is already in context would tell you how much of the 0.25 load rate was the interface.

What bench freezes the judge by construction? Evolution suites need chronological streams, held-out tasks, and a non-editable evaluator. A harness-evolution number that can rise by disabling the judge is not a number.
